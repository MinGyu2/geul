A. engine-phases/run.py 실패 증거 보존 (VERIFIED)
수정 전 원인(HEAD run.py를 같은 가짜 브라우저로 실행, runner-hardening.json):
- Popen 실패(실행 파일 없음 FileNotFoundError, 실행 권한 없음 PermissionError)가 try 밖에서 그대로 전파 → 결과 파일 없음.
- 브라우저가 JSON 배열 등 객체가 아닌 값을 보내면 except 안의 result.update가 다시 예외 → 결과 파일 없음.
- 그 밖에 코드 검토로 확인: kill 뒤 wait 시간 초과·실행 뒤 의존성 재해시 예외·write_text 예외 시 기록 없음, write_text는 실행 중 생긴 파일을 덮어씀,
  브라우저 부모만 SIGTERM하고 자식(WebKit launcher의 setsid driver 포함) 소유권 추적 없음. 메타데이터 실패는 수정 전에도 FAIL 기록됨.
수정:
- 사전 검사(출력 존재·출력 디렉터리·패키지·입력 해시)는 실행 전 사용 오류(exit 2, 기록 없음)로 분리. 그 뒤 모든 시도는 attemptId·단계·실패 범주·예외·
  브라우저 프로세스 기록·서버 상태·수신 결과 수·부분 결과·의존성 안정성·validDiagnosticEvidence를 남긴다. 관찰 못한 값은 null/UNAVAILABLE.
- 최종 status는 정리·의존성 재확인·메타데이터가 끝난 뒤에만 계산. 실패가 하나라도 있으면 DIAGNOSTIC_COMPLETE 불가(브라우저 보고 상태는
  browserReportedStatus로 따로 보존). validate()와 4-arm 계약은 그대로.
- 소유권: start_new_session으로 자기 process group, 실행 중 /proc로 후손을 (pid, 시작 시각)으로 추적, 리더는 마지막에 reap하므로 PGID 재사용 없음.
  정상 종료는 리더 SIGTERM만(launcher가 자기 세션을 닫도록), 남은 소유 후손은 SIGTERM→SIGKILL, 후손 신호는 pidfd로 보내 재사용 PID를 건드리지 않음.
  각 정리 단계(브라우저·로그·서버·프로필)는 독립적으로 실행되고 실패는 판정에 남는다. stop()은 멱등.
  자체 검토로 찾은 결함도 고침: 같은 이름 pending 파일이 이미 있으면 그 파일을 지우지 않음(직접 만든 불완전 파일만 정리).
- 저장: <output>.<attemptId>.pending에 배타 생성+fsync 후 os.link(기존 파일 있으면 실패) → 덮어쓰기 없음. link 실패 시 pending 보존·exit 3,
  쓰기 자체 실패 시 stderr에 EVIDENCE_PERSISTENCE_FAILED와 전체 기록·exit 3(같은 경로 재시도 없음). 성공 0, 진단 실패 1.
- 가설로 남는 한계(INFERRED): /proc 관찰 간격(1초) 사이에 생겼다가 부모를 떠난 setsid 프로세스는 놓칠 수 있다. Linux 전용(/proc, pidfd).
