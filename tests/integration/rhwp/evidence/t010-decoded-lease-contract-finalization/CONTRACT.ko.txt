T010 decoded lease 계약 마무리 — 바뀐 규칙만 (2026-10-25)

범주: VERIFIED=소스 또는 이번 실행, INFERRED=근거 해석, UNVERIFIED=입증하지 못함.
기준: ../t010-decoded-lease-accounting-hardening/CONTRACT.ko.txt(후보 94603ed3). 아래 두 절 외에는 그대로다.

1. 이미지 크기 동일성과 메모리 예약은 다른 계약이다
- 메모리(일반) 계약, 변경 없음: Reservation::authorizes/commit은 actual ≤ reserved를 요구한다. 더 작은 할당은
  실제 크기로 계상한다(예: 40,000 bytes 예약에 32,400 bytes). actual == reserved로 바꾸지 않았다.
- 이미지(무결성) 계약, 신규: 헤더가 크기를 밝힌 이미지는 디코드 결과의 width와 height가 헤더와 각각
  정확히 같아야 한다. bytes가 같아도 모양이 다르면 다르다(예: 100×40 대 40×100, 200×20 대 100×40).
  더 크거나 더 작은 경우 모두 거절한다.
- 구분하는 네 크기(web_canvas decode_image_to_canvas):
  (1) 헤더 크기: canvas_rgba::header_dimensions. reserve_decode가 예약과 함께 돌려준다.
      이전에는 RGBA bytes로 바꾼 뒤 버렸다.
  (2) DynamicImage 크기: image::load_from_memory 결과.
  (3) RGBA 크기: canvas_rgba(&image).dimensions(). Canvas width/height로 그대로 쓴다.
  (4) 예약 bytes: rgba_bytes(헤더 크기).
  검사: (2)=(3)이고 (1)=(3)이어야 한다(check_decoded_dimensions). 그 다음 (4)가 (3)의 bytes를 덮어야 한다(authorizes).
- 생산자 근거(VERIFIED 소스 + 시험): image 0.25.10은 decoder.dimensions()로 버퍼를 만들고 load_from_memory에서
  방향(EXIF) 변환을 적용하지 않는다. 후보도 apply_orientation을 쓰지 않는다. canvas_rgba는 크기를 바꾸지 않는다.
  유효 PNG/JPEG/BMP/TIFF(Luma8 LUT 경로 포함)에서 헤더 = 디코드 = RGBA를 시험으로 확인했다.
  정상적으로 크기를 바꾸는 변환은 없다.
- 헤더 크기 없음(UnknownDimensions): 비교할 기준이 없으므로 기대 크기를 지어내지 않는다.
  기존처럼 디코드 뒤 실제 bytes로 reserve_decoded_bytes를 거친다.
  · 활성 job: 96 MiB guard와 비상주 96 MiB 강제
  · job 없음: 비강제이고 초과를 기록한다
- 구현: canvas_rgba::authorize_decoded(header 예약, decoded 크기, 사후 예약 closure)가 Canvas 할당 전 순서를 정한다.
  · 헤더 크기가 있으면: 크기 동일성 → bytes 승인
  · 없으면: 사후 예약 → bytes 승인
  거절 분류(DecodedRefusal)는 Mismatch, Capacity, Reserve(기존 Refused/Oversize)다.
- 거절 동작:
  · Mismatch와 Capacity는 Decoded::Rejected다. job은 ERROR가 되어 게시하지 않는다.
  · 음성 캐시 entry는 만들지 않는다(영구 decode 실패로 기록하지 않음).
  · 예약은 drop으로 해제되고, Canvas는 만들지 않는다.
  · lease를 반환하지 않고, 이미 살아 있는 공유 backing은 그대로 둔다.
  · 계수기 dimensionMismatches(decodedLedger)를 센다.
  · 할당 뒤의 최종 방어선은 기존 commit 검사다(1회 dispose).
- 도달성: 현재 decoder에서 크기 불일치는 관찰되지 않았다. 불일치 시험은 authorize_decoded에 크기 값을 넣는
  통제된 seam으로만 한다. image 내부를 바꾸지 않았고, 실제 decoder가 그런 결과를 냈다고 주장하지 않는다.

2. 브라우저 증거 버전 필드 타입
- schema: 반드시 있어야 하고, type이 정확히 int이며 값이 1이어야 한다. 완료 status가 FAIL이어도 같다.
- contract:
  · 계약 2 검증: 반드시 있어야 하고, 정확히 int 2여야 한다. 없을 때 계약 1로 내려가지 않는다.
  · 계약 1 검증: 실제 이력 증거(t010-decoded-resource-lease-accounting/browser/*.json)는 필드가 없다.
    그래서 명시적으로 계약 1을 검증할 때만 생략을 허용한다. 있으면 정확히 int 1이어야 한다.
- bool(True/False), float(1.0/2.0), 문자열, None, 배열, 객체, 음수, 0, 지원하지 않는 값은 모두 Invalid다.
  Python의 True == 1, 2.0 == 2 동치를 쓰지 않는다(type(x) is int).
- 검증 계약 인자 자체도 int이고 CONTRACTS에 있어야 한다(CONTRACTS[True]가 CONTRACTS[1]이 되는 일을 막는다).
- dimensionMismatches가 checkpoint에 있으면 정확한 int 0이어야 한다. 이전 계약 2 증거에는 이 필드가 없으므로 선택 필드다.
- 기존 CONTRACTS 1·2의 시험 이름, checkpoint 이름, 수는 바꾸지 않았다.

3. 변경하지 않은 것
Rc<SharedBacking> 소유권, cache/job lease 분리, Weak registry, 마지막 소유자 dispose, commit Result 의미,
authorizes 용량 검사, 96 MiB 한도들, job당 256 lease, 캐시 입장·퇴거, cancel/expiry/close/stale 정리,
Full replay와 원자 게시, 스케줄러, 모든 예산 수치.
