T010 decoded lease 회계 보강 계약 (2026-10-25)

범주: VERIFIED=소스 또는 이번 실행으로 확인, INFERRED=그 근거로 내린 해석, UNVERIFIED=입증하지 못함.
대상: 이전 격리 후보(pinned 1a76570 + upstream-rhwp-decoded-lease-complete.patch, WASM a9222205…)에
upstream-rhwp-decoded-lease-hardening-incremental.patch를 더한 격리 후보(WASM 94603ed3…).
이전 계약(../t010-decoded-resource-lease-accounting/CONTRACT.ko.txt)의 소유권·회계 정의는 그대로이며,
이 문서는 바뀌거나 새로 생긴 규칙만 적는다.

1. 예약과 실제 크기 (P1-A)
- Reservation::commit(backing, actual) -> Result<Rc<SharedBacking>, CommitError>.
  · actual ≤ 예약 bytes일 때만 성공한다. 작으면 실제 크기로 계상하고 나머지 예약은 해제한다.
  · actual > 예약이면 ExceedsReservation{reserved, actual}. 강제·비강제 예약 모두 같다.
    더 큰 할당이 필요하면 새 reserve가 따로 승인해야 한다. 값을 자르거나(clamp) 한도를 올리지 않는다.
  · unique_bytes 또는 unique_count의 checked 덧셈이 넘치면 Overflow(accountingErrors +1).
  · 거절 시: 이미 할당된 backing을 정확히 한 번 dispose하고 lease를 만들지 않는다. 예약은 Reservation
    drop으로 해제된다. uniqueBytes, uniqueCount, created, disposed는 바뀌지 않는다. rejectedCommits +1.
  · 거절된 backing을 성공 lease처럼 돌려주는 경로는 없다(이전 구현의 overflow 분기 제거).
- Reservation::authorizes(actual): 같은 규칙을 할당 전에 검사한다. web_canvas는 decode 결과 크기를
  Canvas 생성 전에 이것으로 검사한다(할당 전 거절, preallocationRejections +1, dispose 없음).
  commit의 검사는 할당 뒤의 최종 방어선이다. 두 경우를 Rust 계약이 구분한다.
- 0 bytes 예약과 0 bytes commit은 유효하다. 0 예약은 1 byte도 승인하지 않는다.

2. 헤더 크기를 알 수 없는 decode (P1-B)
- reserve_decode는 header_dimensions(data)(image 0.25.10의 ImageReader::with_guessed_format +
  into_dimensions; load_from_memory와 같은 format 추정·decoder 생성 경로)로 RGBA를 예약한다.
- 크기를 모르면(UnknownDimensions) decode를 시도할 수는 있지만, 성공한 뒤 Canvas를 만들기 전에
  reserve_decoded_bytes(actual)로 다시 예약한다. 이 함수는 헤더 경로와 같다:
  · 활성 job: 단일 96 MiB guard(Oversize → RESOURCE_LIMIT + 음성 entry), 회수 후
    nonresident + reserved + actual ≤ 96 MiB 강제(Refused → RESOURCE_LIMIT, 음성 entry 없음).
  · 활성 job 없음: 이전과 같이 비강제이고, 한도를 넘으면 unenforcedOverLimit을 센다
    (이전 구현은 이 경로에서 limit=usize::MAX로 넘김을 기록조차 하지 않았다).
  · 이 경로에서는 decoder 메모리가 이미 할당됐을 수 있다. 할당 전 보장은 Canvas backing에만 해당한다.
- 결과 분류(Decoded): Ready / Failed(decode 실패: 음성 entry, browser 이미지 경로 유지) /
  Refused(일시적 예산 거절: 음성 entry 없음, RESOURCE_LIMIT) / Oversize(기존 guard) /
  Rejected(예약을 넘는 실제 크기 또는 overflow: ERROR, 음성 entry 없음, backing 없음 또는 1회 dispose).
  RESOURCE_LIMIT과 ERROR job은 게시하지 않는다(wasm_api poll: Pending이 아니면 finish만 한다).
- 도달 가능성(INFERRED + VERIFIED 시험): image 0.25.10에서 into_dimensions와 decode는 같은 make_decoder를
  쓴다. 그래서 헤더 크기 실패 뒤 decode 성공은 현재 decoder로 도달하지 않는다. canvas_rgba 시험이
  유효 PNG/JPEG/BMP/TIFF, 모든 헤더 위치의 절단·손상, 본문 표본 손상, SVG·GIF·WebP·WMF·EMF·쓰레기
  입력에서 "decode 성공 ⇒ 헤더 크기 = Canvas 크기"와 "(헤더 없음, decode 성공) 조합 0건"을 확인한다.
  미래 decoder가 이 성질을 깨도 위의 사후 예약 때문에 활성 job의 무제한 할당 경로는 생기지 않는다.
- 공개 렌더 API: 이 후보의 renderPageToCanvas·Legacy·Filtered(WithProfile)·Patch·HeaderFooter 미리 보기는 활성 job이
  없으면 1회 poll 호환 job으로 실행된다(wasm_api render_compat_replay). 따라서 공개 Canvas 렌더 중
  decode는 항상 활성 job 안에서 강제된다. 비강제 경로는 job 밖 내부 호출용으로만 남는다(INFERRED, 소스).
  이 성질은 이번 변경 전부터 같았고, 이번 변경은 동기 API에 새 크기 제한을 더하지 않았다.

3. lease 메타데이터 한도 (P2-B)
- MAX_JOB_DECODED_LEASES = 256(job 하나가 PENDING을 넘어 보유하는 서로 다른 decoded lease 키 수).
  근거: decoded 캐시 자체의 entry 한도(DEFAULT_MAX_ENTRIES 256)와 같다. job이 캐시가 상주시킬 수 있는
  수보다 많은 서로 다른 backing을 붙잡을 이유가 없다. browser 이미지 MAX_RESOURCES를 재사용한 것이 아니다.
  MAX_JOBS 8이므로 job lease entry는 최대 2048이다.
- 한도에 닿으면 새 키는 그 job에 보유되지 않는다(attach 거절, decodedAttachRefusals +1). 지금 그리는
  draw-scoped Rc는 그대로 유효하므로 그리기는 끝까지 같다. 그 뒤 비상주이면 drop에서 dispose되고, 다음
  poll에서 키로 다시 찾는다(캐시 → 자기 lease → 살아 있는 다른 소유자 → 새 decode). 이미 있는 키의
  교체는 늘리지 않는다. 기존 lease를 회수하거나 캐시 입장·알림·D4 경로를 바꾸지 않는다.
- Weak registry(Pool.decoded): 등록할 때마다 죽은 entry를 정리하고(등록 직후 크기 = 살아 있는 backing),
  job finish, trimRendererCaches, setRendererCacheBudget 뒤에도 정리한다. 따라서
  registry ≤ 관측된 살아 있는 backing 최대값이고, 종료 정리 뒤 0이다.
  살아 있는 backing ≤ 상주(256) + job 보유(2048) + 그리는 중 1.
- revoke_decoded의 후보 중복 제거는 allocation 주소 색인으로 선형이다(이전은 후보 수의 제곱).
- 통계 추가: decodedRegistryEntries, decodedAttachRefusals, maxJobDecodedLeases, maxJobLeaseEntries
  (jobs), rejectedCommits, postDecodeReservations, preallocationRejections(decodedLedger).

4. 브라우저 증거 validator (P2-A)
- decoded_lease_run.py CONTRACTS가 권위 있는 이름 계약이다. 계약 1 = 이전 32개 시험/43 checkpoint 증거,
  계약 2 = 현재(baseline 6 + candidate 35 = 41개, final 포함 필수 checkpoint 47개 + 보조 snapshot).
  runner는 자기가 제공한 페이지의 계약(CURRENT_CONTRACT=2)으로만 검증한다. 결과가 낮은 계약 번호를
  주장해도 통과하지 않는다.
- PASS 조건: schema 1, 오류 없음, (arm, name) 순서가 계약과 정확히 같음(누락·중복·추가·오귀속·순서
  오류 거절), status는 문자열 'PASS'만, ledger 비어 있지 않음, label은 'candidate:'이고 유일하며 필수
  checkpoint가 계약 순서로 모두 있고 'final'이 마지막, 각 checkpoint의 필드는 bool이 아닌 음이 아닌
  정수이고 정확히 {label, decodedLedger, jobs}.
- 각 checkpoint: unique=resident+nonresident(bytes, count), created−disposed=uniqueCount,
  accountingErrors=0, reserved=0, nonresident ≤ 96 MiB, resident ≤ 캐시 bytes/entries,
  unique ≤ 캐시+96 MiB, peak ≥ unique, registryLive ≤ uniqueCount, jobs.decodedLedger 사본 일치,
  선언 한도(pending 2, resource 256, owned 256 MiB, frame 64 MiB, staging 128 MiB, nonresident 96 MiB) 불변.
  계약 2: maxJobDecodedLeases=256, maxJobLeaseEntries ≤ 256, jobLeaseReferences ≤ 2048,
  registryLive ≤ registryEntries, rejectedCommits=preallocationRejections=0.
- final: unique/count/resident/nonresident/job 참조 0, created=disposed>0, activeJobs·owned·pending·
  registryLive 0, 계약 2에서는 registryEntries·maxJobLeaseEntries 0. cleanup transitions는 baseline,
  candidate 순서로 있고 candidate cleanup jobs가 final과 같다.
- 시험 확장은 CONTRACTS에 이름을 추가하는 방식으로 한다. 수(32/43)를 고정하지 않는다.

5. 변경하지 않은 것
- Rc<SharedBacking> + Weak pool 구조, DecodedLedger, 예약 후 할당, 퇴거 무효화 없음, 마지막 소유자 dispose,
  finish/cancel/expiry/close/invalidation 해제, Full replay와 원자 게시, 캐시 입장 정책, 스케줄러 알림.
- 한도: decoded 캐시 256 MiB/256, browser 캐시 64 MiB/256, browser pool 256 MiB, pending 2, resource 256,
  URL 32 MiB, 단일 decode 96 MiB, 비상주 96 MiB, job 8, deadline 15 s, scratch/backup 각 64 MiB.
  이번 소스에서 다시 확인했고 늘리지 않았다(새 상수 256은 개수 한도이며 bytes 한도가 아니다).
- 모든 bytes는 RGBA backing 추정이다. RSS, GPU, JS heap, decoder 임시 메모리의 상한이 아니다.
