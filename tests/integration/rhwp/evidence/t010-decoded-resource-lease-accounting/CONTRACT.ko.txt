T010 decoded resource lease·메모리 회계 계약 (2026-10-25)

범주: VERIFIED=소스 또는 실제 실행으로 확인, INFERRED=그 근거로 내린 해석, UNVERIFIED=입증하지 못함.
대상 소스: pinned RHWP 1a76570 + upstream-rhwp-exact-gray-lut.patch(ba2242, ae34 실험 소스)에
upstream-rhwp-decoded-lease-incremental.patch를 적용한 격리 후보. 제품 엔진과 submodule은 바꾸지 않았다.

1. 원결함 (VERIFIED, 이번 실행에서 재현)
- ae34의 DECODED_CANVAS_CACHE는 BoundedCache<HtmlCanvasElement>였다. get은 원시 handle을 clone하고,
  remove는 Release(width/height=0)를 호출했다. clone은 소유권이 아니다.
- 다른 job의 정상 입장이 LRU 퇴거를 일으키면 보관된 handle이 0×0이 된다.
  baseline-raw-handle-invalidated-by-unrelated-eviction(Chrome/WebKit PASS).
- 실제 PENDING 경계에서도 같다. 대기 중인 job이 쓴 decoded handle이 다른 job의 퇴거로 0×0이 되고,
  다음 poll에서 다시 decode한다(baseline-pending-job-handle-invalidated, -redecodes-after-eviction).
- 캐시에 들지 않은 임시 Canvas는 그린 직후 release되므로 PENDING 반환 전에 이미 0×0이다
  (baseline-temporary-released-before-pending-return).

2. 소유권 표현 (VERIFIED: 소스)
- surface_cache.rs(순수 Rust):
  Backing::dispose, DecodedLedger, Reservation, SharedBacking<B>, impl Release for Rc<SharedBacking<B>>(no-op).
- render_job.rs: DecodedLease = Rc<SharedBacking<HtmlCanvasElement>>.
  Job.decoded: HashMap<ImageKey, DecodedLease>, Pool.decoded: HashMap<ImageKey, Weak<…>>(조회 전용).
- web_canvas.rs: DECODED_CANVAS_CACHE = BoundedCache<DecodedLease>, DECODED_LEDGER(thread-local Rc).
  HtmlCanvasElement::dispose가 0×0을 만든다. 이전 Release for HtmlCanvasElement는 제거했다.
- 기존 browser 이미지 구조(Rc<ImageResource> + Weak pool)와 같은 방식이다. 별도 lease 관리자는
  만들지 않았다. 다만 browser 이미지 ledger(MAX_OWNED_BYTES)와 decoded ledger는 분리된 예산이다.

3. 전이
(a) 생성: cache miss이고, 같은 키의 job lease나 살아 있는 소유자가 없을 때만 decode한다.
    header 크기로 reserve(RGBA w×h×4)한 뒤 할당하고, 성공하면 commit(actual)으로 고유 backing 1개가 된다.
    실패(디코드 실패, 그리기 실패)하면 commit하지 않은 Canvas를 dispose하고, 예약은 drop되며 해제된다.
(b) 캐시 입장: 기존 BoundedCache.insert와 입장 정책을 그대로 쓴다. 캐시는 자기 Rc를 가진다.
(c) 퇴거·trim·예산 축소: 캐시의 Rc만 놓는다(Release no-op). 다른 소유자가 없으면 그 drop이
    마지막 소유자가 되어 dispose된다.
(d) job lease: poll 중 decoded_canvas가 활성 Pending job에 attach_decoded로 Rc를 준다.
    PENDING 반환을 넘어 유지되며, finish(COMPLETE/CANCELED/ERROR/RESOURCE_LIMIT)나 Job drop에서
    map 전체를 놓는다.
(e) 조회 순서: cache.get(통계·빈도는 기존과 동일) → 활성 job의 lease → Weak pool(다른 job이 가진
    live backing). 캐시에서 찾지 못했지만 live lease가 있으면, 기존 엔진이 재decode 결과를 캐시에
    제출하던 자리에서 같은 backing을 같은 insert로 제출한다. 그래서 입장·퇴거 결과가 baseline과
    같다(decoded-cache-policy-identical-to-baseline: 두 브라우저에서 캐시 통계 JSON 전체가 일치).
(f) job 없는 동기 그리기(legacy API): 반환된 draw-scoped Rc만 있다. 비상주이면 그리기 직후 drop되어
    dispose된다. 기존 즉시 release 동작과 같다.
(g) 마지막 소유자: SharedBacking::drop에서 정확히 한 번 dispose하고 회계를 반영한다. Rc 의미와
    disposed 플래그로 이중 해제가 없다. 해제된 backing은 Weak upgrade로 돌아오지 않는다.

4. 회계 장부 정의 (bytes는 추정이며 RSS·GPU·브라우저 allocator 측정값이 아님)
A 고유 decoded backing: ledger.uniqueBytes/uniqueCount. 참조 수와 무관하게 할당당 1회.
B 캐시 상주: 디코드 캐시 entry(resident_capacity_where). decoded 캐시에는 pending entry가 없다.
C job lease 참조: jobLeaseReferences/jobLeaseReferenceBytes. 참조 관찰값이며, job 사이 중복이
  있으므로 A에 더하지 않는다.
D 비상주 decoded = A − B(job 보유, 퇴거 뒤에도 lease가 남은 것, 그리기 중 임시).
E 예약: reservedBytes. poll 사이 checkpoint에서는 항상 0이다.
F browser 이미지: 기존 Pool.resources unique ownedEstimatedBytes(MAX_OWNED_BYTES 256 MiB),
  pending 2개, 256개 한도. 변경하지 않았다.
G tree·resolved payload: PageLayerTree::payload_estimate. arena 이미지/SVG(capacity), image node
  data, 변환/워터마크 payload, RawSvg 문자열, 독점 font blob(Arc 공유분은 sharedFontBytes로 분리)을
  센다. text·geometry·map은 빼므로 하한값이다. 관찰용이며 강제하지 않는다. tree는 poll 끝에 drop된다.
H decode 임시: peakDecodeTransientEstimatedBytes = DynamicImage 바이트 + RGBA Vec + ImageData 복사.
  scratch/backup은 기존 temporary/backup counter(각 64 MiB, staging 128 MiB)를 그대로 쓴다.

5. 예산 (실제 소스 값, 증가 없음)
- decoded cache 256 MiB / 256 entry, browser cache 64 MiB / 256 entry, 단일 entry = 예산/4.
- browser pool MAX_OWNED_BYTES 256 MiB, MAX_PENDING 2, MAX_RESOURCES 256, MAX_URL_BYTES 32 MiB,
  MAX_DECODED_BYTES 96 MiB, MAX_JOBS 8, deadline 15 s, MAX_FRAME_BYTES 64 MiB(scratch, backup 각각).
- 신규 상수 MAX_NONRESIDENT_DECODED_BYTES = MAX_DECODED_BYTES(96 MiB): 기존 단일 decode 한도를
  비상주 decoded 전체에 재사용한다. 새 한도 증가가 아니다.
- 불변식 1: D ≤ 96 MiB(모든 엔진 작업 경계). 불변식 2: B ≤ decoded cache 예산.
  따라서 A ≤ cache 예산 + 96 MiB이다. 이전 엔진의 최대값(상주 + 임시 1개 ≤ 96 MiB)과 같은 상한이다.
- 강제 방법:
  · job decode 전 D + 예약 + t ≤ 96 MiB인지 checked 산술로 검사한다. 넘으면 먼저 revoke_decoded를 실행한다.
  · revoke는 대기 job의 비상주 lease부터, 다음은 활성 job의 이전 lease를 회수한다.
    그리는 중인 lease와 상주 backing은 회수하지 않는다. 회수한 lease는 모든 job map에서 빠지므로,
    dispose된 handle을 가진 job은 없다. 이후 그리기는 키로 다시 찾는다.
  · 캐시 insert로 퇴거가 일어나 상주가 비상주로 바뀌면 enforce_nonresident_bound로 다시 맞춘다.
    재분류는 새 할당이 아니므로 A는 늘지 않는다.
  · 그래도 거절되면 RESOURCE_LIMIT이며, 음성 캐시 entry는 만들지 않는다. 회수 뒤에는 단일 이미지가
    t ≤ 96 MiB(기존 guard)를 지키므로 실제로는 도달하지 않는다(INFERRED, refusedReservations=0 관찰).
  · 기존 guard: job 중 rgba > 96 MiB는 RESOURCE_LIMIT과 음성 entry(변경 없음).
  · legacy 동기 API(활성 job 없음)는 이전처럼 크기 제한 없이 그린다. 한도를 넘으면
    unenforcedOverLimit을 센다. 조용히 넘는 경우는 없다.
  · 헤더로 크기를 알 수 없는 decode 시도(SVG 등 Rust 미지원 형식)는 unreservedDecodes로 센다.
    실패하므로 backing은 없다. 성공하면 commit 시점에 실제 크기를 기록한다.
- 용량 알림: decoded 용량을 기다리는 작업은 없다(decoded는 PENDING을 만들지 않는다). 그래서 decoded
  해제는 알림을 보내지 않는다. browser 알림 규칙은 그대로다
  (decoded-release-no-false-capacity-notification, scheduler 73/73).

7. 경계와 한계
- 동기 poll 내부(tree 직후, decode 중, replay 뒤 게시 전)에는 취소 지점이 없다. 그런 지점은 만들지
  않았다. lease가 실제로 쓰이는 경계는 poll 반환(PENDING)과 terminal이다.
- Preparing → ResourcesReady 상태, tree 보존, cursor, worker는 구현하지 않았다.
- ImageKey는 실제로 decode하는 bytes(변환/워터마크 결과 포함)의 FNV64+표본 mix+길이다. 암호학적
  해시가 아니므로 충돌 가능성은 기존과 같다(UNVERIFIED: 충돌 부재). filter/밝기는 그리기 시 ctx에
  적용되므로 같은 decoded backing을 공유해도 된다. 미래 prepared-resource 재사용은 render_image의
  변환 결과 bytes를 키로 써야 한다.
- 대기 job의 비상주 lease 보유는 기회적이다. 예산 압박 때 경계에서 회수되며, 이후 다시 decode한다
  (pressure 시험이 픽셀 동일성으로 확인).
