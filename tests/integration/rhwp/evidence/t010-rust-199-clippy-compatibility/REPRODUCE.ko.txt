T010 Rust 1.99 호환성 재현

환경 확인과 보존
ROOT는 git rev-parse --show-toplevel로 확인한다. SCRATCH는 새 외부 작업 폴더,
TARGET은 기존 target/rhwp-wasm이다. 실제 이전 source/후보/기준은 덮어쓰지 않는다.
rustc --version / cargo --version / rustc --print sysroot 및 sysroot/lib/rustlib의 설치 target을 확인한다.
이번 실행은 Rust1.99.0, cargo1.99.0, host와 wasm32-unknown-unknown이다.
CARGO_NET_OFFLINE=true CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=2 CARGO_TARGET_DIR="$TARGET"를 설정한다.
모든 Cargo build/test/clippy는 --locked --offline다. upstream rust-toolchain.toml의1.93.1은 그대로 둔다.
PATH의 실제 compiler가 기존 Nix1.99인지 먼저 확인하며 rustup이나 설치기는 호출하지 않는다.

소스 준비 (두 방식 중 하나)
1) 현재 사용 가능한 이전 source를 재사용한다. src/crates와 루트 메타데이터는 독립 복사하고
불변 samples/tools/bindings/test 입력은 hardlink로 재사용했다. 기존 후보 패키지와 .git은 복사하지 않았다.
수정 전에 이전 src digest4be2c644…와 실제 후보8fb447…를 확인한다.
새 source에서 git apply --check <호환 patch>, git apply <호환 patch> 순으로 적용한다.
2) 이전 export가 없다면 기존 cache-concurrency/prepare.py의 --prepare-only --no-opt와
새 upstream-rhwp-rust-199-complete.patch로 고정 submodule에서 새 외부 source를 내보낸다.
이는 재현 절차이며 이번 실행에서는 불필요한 source 전체 재내보내기를 하지 않았다.
Cargo.lock/모든 Cargo.toml/rust-toolchain.toml은 이전 source와 바이트 동일해야 한다.

실패 재현과 최소 교정
기존 source의 복사본에서 아래 strict 네 명령을 실행하면 workspace2/2, RHWP39/38 진단으로 exit101이다.
원본 JSONL·stderr는 scratch의 *-before 파일로 보존했다. correction-inventory.json은 타깃 중복을 제거한다.
첫 교정 뒤 RHWP 단독은 통과하지만 workspace에 chart collapsible_match1건이 드러난다(after1 증거).
이를 교정한 after2가 최종 소스다. 추가 suppress/manifest/lock/feature 변경은 없다.

Strict Clippy (격리 source 작업 디렉터리)
cargo clippy --locked --offline --workspace --lib --message-format=json -- -D warnings
cargo clippy --locked --offline --workspace --lib --release --target wasm32-unknown-unknown --message-format=json -- -D warnings
cargo clippy --locked --offline -p rhwp --lib --no-deps --message-format=json -- -D warnings
cargo clippy --locked --offline -p rhwp --lib --no-deps --release --target wasm32-unknown-unknown --message-format=json -- -D warnings
네 exit0과 진단0이 모두 필요하다. JSON의 build-finished 성공 및 process exit를 함께 확인한다.

Rust/Python 검증
변경32파일은 rustfmt --edition 2021 --config skip_children=true --check로 검사한다.
암호 교정 전: cargo test --locked --offline -p rhwp-password-crypto --lib -- --nocapture
수정 전 matrix198입력 digest를 실제로 확보한 뒤 새 golden assertion을 추가했다. 기존 외부벡터도 유지했다.
RUSTFLAGS='-C link-arg=-fuse-ld=bfd' cargo test --locked --offline --workspace --lib
이번 전체4169 PASS/13 ignored/0 FAIL이다. 이는 parser/core/renderer 등32파일 변경에 따른 확장 검증이다.
Linker 옵션은 경고 억제가 아니다. 같은 전체 suite를 이유 없이 반복하지 않는다.
ROOT에서 python3 -m unittest discover -s tests/integration/rhwp/rust-199-clippy-compatibility
identity의 src 정렬 계약과 workspace crypto 포함을 검사한다. Python security86도 실행했다.
기존 terminal_probe.py --source "$SOURCE"로 실제 marker 함수5개를 host에서 검사한다(전체 DOM 시험 아님).
cache-concurrency/unit.py --source "$SOURCE/src/renderer/surface_cache.rs" --suite current,
그리고 --contract decoded_lease_contract.rs / decoded_lease_hardening_contract.rs / ownership_contract.rs /

패치 재현과 신원
python3 tests/integration/rhwp/rust-199-clippy-compatibility/patches.py --source "$SOURCE" \
 --previous "$PREVIOUS" --output <새 검증 폴더>
완전 patch는 고정 RHWP에, compatibility patch는 직전 source에 각각 독립 적용한다.
두 source의 workspace 입력 digest가 새 source와 동일해야 한다. 새 identity.py는 src 외에 crypto/chart 등
workspace crate와 선언된 tools/bindings Rust 및 Cargo 메타데이터까지 포함한다.
과거 src-only digest도 기존 Path 정렬 계약으로 별도 계산한다. 두 범위의 hash를 혼동하지 않는다.
독립 검증 중 처음 만든 문자열 정렬 구현의 불일치는 교정했고 회귀2개로 고정했다.
원본 소스가 바뀐 것이 아니며 최초 진단 결과는 scratch에 남겼다.

기존 도구만 사용하는 빌드
python3 tests/integration/rhwp/rust-199-clippy-compatibility/build.py --source "$SOURCE" \
 --target-dir "$TARGET" --bindgen "$EXISTING_BINDGEN" --output "$CANDIDATE" --record-dir <새 빌드기록 폴더>
EXISTING_BINDGEN은 설치된0.2.127 바이너리의 실제 절대 경로다. wasm-pack 설치 단계와 wasm-opt는 호출하지 않는다.
실제 command는 cargo build --locked --offline --release --target wasm32-unknown-unknown --lib다.
source 전후 snapshot 일치와 실제 JS/WASM/d.ts/ENGINE SHA를 확인한다. 이전 패키지를 새 신원으로 재사용하지 않는다.

실제 브라우저 (기존 하네스는 수정하지 않음)

render-preparation/run.py --baseline "$REFERENCE" --reference "$REFERENCE" --candidate "$CANDIDATE" \

REFERENCE는 실제 WASM eaa88f65…가 확인된 기존 Rust1.99 재구축 기준이다. 재빌드하지 않았다.
49계약/42RGBA(화학7쪽×cold-warm×3), hardening10+3, ownership52/scheduler73의 기존 의미를 유지한다.
원래 ae34 oracle과의 직접 비교는 UNVERIFIED다. 빈 reference/불완전 비교는 통과로 취급하지 않는다.

보안/커밋/최종 HEAD 검사
python3 scripts/check-sensitive-info.py --all / --staged / --history
설치된 Gitleaks8.30.1로 .gitleaks.toml을 적용해 history/tree/staged를 검사한다.
tree는 추적 파일만 상대경로로 복사한 task-owned mirror다. 검사 후 새 mirror만 제거하고 원본/로그는 보존한다.
기존 gitleaks_allowlist_negative_check.py로24음성경우를 검사하고 기존 보안 Python86을 실행한다.
git diff --check와 시작 HEAD 대비 새 evidence/새 compatibility harness 외 경로 변경0 및 두 gitlink를 검사한다.
정상 commit 훅이 기존 캐시로 실행되는지 확인하고 구현·증거를 로컬 커밋한다. push는 하지 않는다.
그 후 실제 최종 HEAD에 대해 아래를 실행한다:
python3 tests/integration/rhwp/rust-199-clippy-compatibility/verify_final.py --base <시작HEAD> \
 --source "$SOURCE" --candidate "$CANDIDATE" --gitleaks "$EXISTING_GITLEAKS" --output-dir "$SCRATCH/postcommit-final"
이는 두 전체 이력 검사를 다시 실행하며 최종 HEAD 안정성/보호 경로/gitlink/커밋patch/실제후보/소스 신원을 검증한다.
최종 postcommit 결과는 해당 외부 폴더에 보존하고 최종 응답에 실제 HEAD와 파일 링크를 제공한다.
그 결과를 커밋하면 검사 대상 HEAD가 다시 바뀌므로 pre-commit 결과와 혼동하지 않는다.
